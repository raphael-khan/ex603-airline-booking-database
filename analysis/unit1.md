### Modelling Justification

The database model was designed around the main activities of an airline booking platform: maintaining passenger information, managing flights and airports, recording bookings, and representing the airports associated with each flight. I chose surrogate integer primary keys for `PASSENGER`, `FLIGHTS`, and `BOOKINGS` because each record needs a stable identifier that is independent of descriptive attributes. For example, passenger names and email addresses can change, while `passenger_id` should remain the same throughout the passenger's history. Similarly, `flight_id` and `booking_id` provide simple and reliable identifiers for flights and individual bookings. For `AIRPORTS`, `airport_id` serves as the unique identifier for each airport. The `FLIGHT_ROUTES` relation uses a composite primary key consisting of `flight_id` and `airport_id`, which prevents the same airport from being associated with the same flight more than once.

The foreign key relationships enforce referential integrity between the relations. A booking must reference an existing passenger and an existing flight, while every flight-route record must reference an existing flight and airport. I chose `ON DELETE RESTRICT` for `BOOKINGS.passenger_id` and `BOOKINGS.flight_id` because deleting a passenger or flight that has existing bookings could destroy important historical information or leave bookings without a valid reference. The same behavior is used for `FLIGHT_ROUTES.airport_id` because an airport should not be removed while it is still being used by an existing route. In contrast, `FLIGHT_ROUTES.flight_id` uses `ON DELETE CASCADE` because a route association has no independent meaning once its flight is deleted. Removing the flight should therefore automatically remove its dependent route records.

I chose to enforce several business rules at the database level rather than relying entirely on the application. Primary keys and foreign keys are enforced in the schema because referential integrity should not depend on individual application processes behaving correctly. I also enforce unique passenger email addresses, positive flight duration, nonnegative fares, and valid airport roles. The `airport_role` attribute is restricted to `DEPARTURE` or `ARRIVAL`, preventing invalid values from being stored. In addition, each flight is expected to have exactly one departure airport and one arrival airport. These constraints help ensure that the database represents valid airline data regardless of which application or process is writing to it.

The model intentionally avoids adding unnecessary entities or relationships. Airport city and country are stored as descriptive attributes rather than creating separate city and country relations. This keeps the schema simple while still supporting useful queries such as finding flights associated with airports in a particular city or country. Overall, the design prioritizes data integrity, clear relationships, and efficient support for the platform's primary read and write operations.

### Reflection

One design decision that another designer could reasonably make differently is how the relationship between flights and airports is modeled. I chose to use the `FLIGHT_ROUTES` junction relation with an `airport_role` attribute to identify each airport as either `DEPARTURE` or `ARRIVAL`. Another reasonable design would be to store `departure_airport_id` and `arrival_airport_id` directly in the `FLIGHTS` relation.

I chose the junction-table approach because it aligns with the required junction role in the project and keeps airport associations in one place. It also makes the relationship between flights and airports explicit and allows the model to be extended if the platform later needs to represent additional airport roles. From a read perspective, a flight's route can be retrieved by joining `FLIGHTS`, `FLIGHT_ROUTES`, and `AIRPORTS`. From a write perspective, adding or changing an airport association only requires updating the route relationship rather than changing the structure of the `FLIGHTS` relation.

The direct foreign-key approach would make the common query for a flight's origin and destination simpler, so it could be a reasonable alternative for a system where those reads are the primary concern. However, I preferred the junction design because it better represents the relationship itself and satisfies the project's required relational pattern.
